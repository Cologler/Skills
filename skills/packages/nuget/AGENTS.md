# NuGet Package Skills

1. In each skill's `Prerequisite`, assume the consuming project already has the package installed. Only check the affected project's dependencies if a compiler error suggests the package is missing. If it is absent, ask for user approval before installing it. Include `dotnet add <project.csproj> package <FullPackageId>` with the actual NuGet package ID, so this guidance also applies when the skill is copied elsewhere.
2. Describe the triggering programming task directly, without assuming the agent already knows or has chosen the package, or has decided to reduce boilerplate. Keep descriptions concise; put package features and implementation details in the body.
3. Use `Why this package is useful` to identify the repetitive operation the package replaces and its concrete benefits. Put actual behavior and usage details in `Usage`, related features in its subsections, and relevant limitations in `Notes` when needed. Keep benefits separate from behavior and avoid repeating the same information across sections.
4. Prefer short code examples over lengthy explanations. Omit routine standard-library imports, but retain package imports and framework imports that clarify the example. Add comments only when they explain a non-obvious reason or usage constraint.
5. Defer routine language, SDK, and IDE version requirements to package metadata and official documentation. Keep constraints that directly affect correct use, such as attribute placement, callback signatures, and framework-specific behavior.
6. Read the package's official README when authoring or revising a skill, and verify examples and behavior against official sources. Keep common usage and essential correctness boundaries self-contained. Defer uncommon details to the project's documentation through the required `Further reference` section, and instruct readers not to fetch information already covered in the skill.
