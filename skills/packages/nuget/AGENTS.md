# NuGet Package Skills

1. Do not open a skill with a standalone `Prerequisite` section, installation commands, or package-reference configuration (such as `PrivateAssets="all"` for source generators). Instead, put a brief fallback note at the end of `Notes`: assume the consuming project already references the `<FullPackageId>` NuGet package, only check the affected project's dependencies if a compiler error suggests it is missing, and ask for user approval before adding it. Include the exact NuGet package ID so this guidance remains self-contained when the skill is copied elsewhere.
2. Describe the triggering programming task directly, without assuming the agent already knows or has chosen the package, or has decided to reduce boilerplate. Keep descriptions concise; put package features and implementation details in the body.
3. Use `Why this package is useful` instead of an exhaustive `When to use` rule list: explain why the package is valuable so the agent can judge whether it fits each task. Identify what repetitive operation the package replaces, and emphasize durable benefits beyond typing less, such as preventing mistakes or maintenance drift and improving readability for review and long-term maintenance. When authoring or revising a skill, also suggest to the user any additional benefits or trade-offs that may be worth adding to this section.
4. Put actual behavior and usage details in `Usage`, related features in its subsections, and relevant limitations or trade-offs along with the missing-package fallback note in `Notes`. Keep benefits separate from behavior and avoid repeating the same information across sections.
5. Prefer short code examples over lengthy explanations. Omit routine standard-library imports, but retain package imports and framework imports that clarify the example. Add comments only when they explain a non-obvious reason or usage constraint.
6. Defer routine language, SDK, and IDE version requirements to package metadata and official documentation. Keep constraints that directly affect correct use, such as attribute placement, callback signatures, and framework-specific behavior.
7. Read the package's official README when authoring or revising a skill, and verify examples and behavior against official sources. Keep common usage and essential correctness boundaries self-contained. Defer uncommon details to the project's documentation through the required `Further reference` section, and instruct readers not to fetch information already covered in the skill.
